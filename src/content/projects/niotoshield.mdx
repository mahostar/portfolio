## Problem

NiotoShield asks a difficult edge-AI question: how can a vehicle-security device decide quickly enough to be useful, without treating every detected face as trustworthy? Face recognition alone is not sufficient. A printed portrait or replayed screen can pass a recognizer unless liveness is checked first.

The system therefore needs two distinct gates: an anti-spoofing decision before identity matching, then a local authorization decision after a match. It also needs a safe way to refresh the enrolled identities without shipping a new firmware image every time a profile changes.

## What I built

I built NiotoShield as a graduation project that joins a camera, Raspberry Pi software, custom electronics, cloud-backed enrollment, and a vehicle-access output. The device is provisioned with a product key, synchronizes its owner profile from Supabase, converts the approved images into local face embeddings, and keeps the recognition path local at scan time.

The public [NiotoShield firmware repository](https://github.com/mahostar/NiotoShield-Firmware) documents the provisioning and recognition side: environment-based credentials, product-key lookup, image download, update tracking, embedding generation, and local matching. It deliberately avoids keeping the downloaded enrollment photos after embeddings are generated.

The liveness side became [EasyShield](/projects/easyshield), a separate open-source anti-spoofing project. That separation matters: NiotoShield owns the access-control flow, while EasyShield owns the data preparation, model training, evaluation, and live Real/Fake inference workflow.

### A two-gate vision path

The runtime in `face_security.py` captures a short set of face images. EasyShield evaluates the frames for spoofing before the recognizer compares identity embeddings. Real predictions must outnumber fake predictions; a failed liveness decision ends the flow. A verified face is compared with the locally stored enrollment vectors, and a match at or above the configured similarity threshold authorizes the access output.

The design is intentionally ordered this way. Running identity matching on an unverified face would make the recognizer the first security boundary, which is the wrong place to detect a printed or replayed attack. Anti-spoofing reduces that risk before the access relay is involved.

### Enrollment and synchronization

The firmware uses the device product key to retrieve the associated user profile. It compares the profile's `updated_at` value with its last successful synchronization, so it only rebuilds the local image and embedding data when the enrollment changes. This keeps the recognition path independent from round-trip cloud latency while allowing a profile to be updated remotely.

InsightFace generates the face embeddings, which are stored with metadata for later comparison. The runtime `face_security.py` uses `FACE_MATCH_THRESHOLD = 0.6`, while the README describes `0.5` and an older system diagram shows 70%. The new figure follows the executable runtime. A deployment should unify these representations and validate its chosen threshold against false-accept and false-reject rates.

### CUDA is part of the deployment contract

The acceleration story is about the whole inference stack, not a CUDA label on a project. EasyShield documents a CUDA 11.8 and cuDNN 8.9.6 setup with a CUDA-enabled PyTorch build (`cu118`) for its YOLOv12-nano anti-spoofing model. Its published 8,000-image evaluation reports a 75.47 ms average inference time, while the hardware sequence diagram frames a sub-80 ms analysis target. Those figures describe the model evaluation and design target; they are not a guarantee of end-to-end latency on every device or camera.

For an NVIDIA edge target such as Jetson, the deployment path is JetPack, CUDA, cuDNN, and TensorRT. CUDA accelerates the neural-network work; camera capture, decoding, data movement, thresholding, cloud synchronization, and relay actuation still have their own cost. Treating these as separate stages is how I reason about whether a vision pipeline can feel real-time rather than only reporting a fast model benchmark.

The reviewed Raspberry Pi runtime explicitly loads the liveness model on CPU. The CUDA/cuDNN environment describes model training and a possible NVIDIA target, rather than acceleration already active in this Pi code. A committed TensorRT engine or INT8 calibration pipeline was not established by the reviewed source.

## Result

NiotoShield demonstrates a complete security chain: provisioned profile sync, local embedding generation, anti-spoofing before matching, a thresholded identity decision, and a physical authorization step. The result is a more credible edge-security architecture than a standalone face-recognition demo because the model, identity store, update mechanism, and output action all have a defined place.

EasyShield supports the model side with its own [open-source repository](https://github.com/mahostar/EasyShield_v2.5): YOLOv12-nano training tools, MTCNN-assisted face preparation, live testing, and CUDA-aware environment guidance. Together, the two repositories show the link between model work and a hardware system that can use it.

## What I would improve

The next technical milestone is a measured edge deployment. I would profile camera-to-decision latency stage by stage on the target hardware, publish the camera resolution and batch policy, and separate anti-spoofing latency from face-embedding and similarity latency. On Jetson, I would export and validate a TensorRT engine, test FP16 first, then evaluate INT8 only with a representative calibration set and accuracy checks.

I would also unify the matching threshold across the design diagram and firmware, test replay attacks and poor lighting, rotate product credentials, make synchronization recover safely after interruption, and document the relay's fail-safe behavior. Those details turn a promising vision pipeline into an auditable access-control system.

## Abstract
TPMS Studio converts parameterized implicit fields into finite, closed triangle meshes through a reproducible desktop workflow. Periodic equations describe the geometry; cell counts and domain dimensions set its spatial frequency; a scalar-field band creates material around the level surface. A negative exterior padding layer closes intersections at the sampled domain boundary before marching-cubes extraction. Vertex cleanup, normal correction, and topology inspection complete the path to preview and STL export. This paper traces that implementation, separates geometric fidelity from mesh closure, and reports a fresh source-copy check of six built-in presets. All six checked meshes were watertight under the stated test configuration.

**Keywords:** implicit geometry; TPMS; marching cubes; shell generation; boundary closure; mesh topology.

## System specification
### 2.1 A geometry engine with an observable desktop interface
The reviewed implementation is the Python engine in `tpms_generator.py` and its PyQt5/PyVistaQt interface in `GUI_API.py`. The repository also contains a React/Three.js educational viewer; that viewer is a separate presentation path. The mesh-generation architecture below describes the desktop tool.

The API accepts a `TPMSConfig`, returns a `TPMSResult`, and exports its retained mesh. The GUI exposes template and custom-expression controls, requests generation through a worker thread, and presents the result as a colored surface or wireframe. API configuration supports independent dimensions and cell counts on each axis; the reviewed GUI uses one size and one cell count for all three axes.

| Configuration | Geometric or computational role |
| --- | --- |
| Formula | Gyroid, Primitive, Diamond, IWP, Neovius, or BCC; custom expressions are also supported |
| Physical dimensions $L_x,L_y,L_z$ | Coordinate scale of the sampled domain |
| Cell counts $n_x,n_y,n_z$ | Repetition density along each axis |
| Isovalue $C$ | Offset applied to the evaluated field |
| Field-band parameter $\tau$ | Width of the retained interval in scalar-field values |
| Grid resolution $r_x,r_y,r_z$ | Sampling density before surface extraction |
| Target file size | Heuristic input to automatic resolution selection |

## Method
### 3.1 Spatial frequency makes the model reproducible
For axis $a\in\{x,y,z\}$, the engine derives angular frequency from the requested number of repetitions and physical domain length:

$$
\omega_a=\frac{2\pi n_a}{L_a},\qquad \theta_a=\omega_a x_a.
\tag{1}
$$

This binds the periodic rule to physical coordinates. Increasing cell count while holding domain length fixed produces smaller repeated cells. Increasing domain length while holding cell count fixed increases cell size. The main presets use these axis-specific frequencies.

For the Gyroid approximation, the sampled field is

$$
\begin{aligned}
F(\mathbf x)&=\sin\theta_x\cos\theta_y\\
&\quad+\sin\theta_y\cos\theta_z\\
&\quad+\sin\theta_z\cos\theta_x-C.
\end{aligned}
\tag{2}
$$

The trigonometric representation is an implicit approximation used to generate TPMS-like geometry. It does not constitute a numerical proof of zero mean curvature. The engine evaluates the base preset with zero offset and then subtracts the configured $C$ once. This makes the isovalue a geometric input rather than a display adjustment.

### 3.2 Material is a band around the level surface
A zero level set has no solid thickness. The generator transforms the field into a sign convention suitable for a solid shell:

$$
\begin{aligned}
S(\mathbf x)&=\frac{\tau}{2}-|F(\mathbf x)|,\\
\Omega_{\mathrm{solid}}&=\{\mathbf x:S(\mathbf x)\geq0\}.
\end{aligned}
\tag{3}
$$

The two sides of the shell lie near $F=\pm\tau/2$. The parameter named `wall_thickness` in the source acts directly on field values. Because $F$ is not a signed-distance function, this parameter does not generally produce a constant thickness in millimetres. Where the field has a nonzero gradient and the band is sufficiently narrow, a local first-order estimate is

$$
t_{\mathrm{local}}(\mathbf x)\approx\frac{\tau}{\|\nabla F(\mathbf x)\|}.
\tag{4}
$$

This distinction explains why numerical resolution and physical feature inspection both matter. A band can be mathematically well specified while its local wall width varies through the part. A constant-distance offset would require a distance-field construction or another thickness-control method.

### 3.3 Boundary closure is an explicit construction
The sampled shell may intersect the sides of the finite box. Extracting only the interior can leave boundary loops open. The engine pads every side with one voxel of exterior value $S=-1$, then extracts the zero level. Interpolation between interior solid values and the negative exterior creates closure surfaces at those cuts.

Marching cubes converts local grid-cell crossings into vertices and triangular faces. The resulting padded-grid vertex coordinate $v_a$ is transformed into physical units by

$$
x_a=(v_a-1)\frac{L_a}{r_a-1}.
\tag{5}
$$

Subtracting one removes the padding-index offset; dividing by $r_a-1$ accounts for the inclusive grid endpoints. Closure occurs between the boundary samples and the exterior layer, so the final mesh bounds can extend slightly beyond the nominal sampling box. Exact manufactured extents should be checked on the extracted mesh.

### 3.4 Resolution is selected before extraction
The automatic controller estimates triangle count from a requested binary-STL payload and approximates the relation between triangles and voxels. With target size $B$ in decimal megabytes, its initial cubic-grid estimate follows

$$
\begin{aligned}
\widehat T&=\frac{10^6B}{50},\\
\widehat V&=\frac{\widehat T}{0.45},\\
r_0&=\max\!\left(\lfloor\widehat V^{1/3}\rfloor,20n_{\max}\right),\\
r&=\min(300,r_0).
\end{aligned}
\tag{6}
$$

The estimate uses 50 bytes per binary-STL triangle and 0.45 triangles per voxel. Neither the realized triangle count nor the final file size is fixed by this estimate. The 300-point cap takes precedence when the cell-density floor exceeds it. Explicit resolution bypasses this automatic rule. The ordinary generation path does not automatically decimate the extracted mesh.

## Implementation
### 4.1 State and execution boundaries
`TPMSMainWindow.start_generation` gathers controls into a configuration, disables the Generate button, and starts `GenerationWorker`. Its `run` method calls `TPMSGeneratorAPI.generate`. Completion or error signals return control to the GUI, where the button is restored and a successful result becomes the current preview/export object.

Within the engine, `ResolutionController` chooses the grid, `TPMSEngine` selects the scalar-field function, and `MeshGenerator` builds the band and extracts geometry. NumPy evaluates full three-dimensional coordinate arrays. This vectorization avoids a Python loop over individual grid points, but its memory cost still grows with the number of sampled voxels. Raising every axis resolution increases the volume of work cubically.

### 4.2 What the topology report establishes
After extraction, the API merges vertices and fixes normals through Trimesh. It reports `mesh.is_watertight` and `mesh.euler_number`. Watertight edge connectivity means every mesh edge is incident to two faces. A porous solid can contain many tunnels and remain watertight: the tunnel walls are part of a closed boundary, rather than missing faces.

The Euler characteristic is

$$
\chi=V-E+T,
\tag{7}
$$

where $V$, $E$, and $T$ are mesh vertex, edge, and triangle counts. The source stores this value under a field named `genus`; this paper reports it as Euler characteristic. Converting it into genus requires additional assumptions about connectedness and orientability.

The API can return success even when watertight status is false, and export checks generation success rather than imposing a topology gate. Curvature and periodicity validator modules exist, but the reviewed main path does not execute those advanced checks. The result is an inspectable generation and topology workflow, with closure status available for each mesh.

## Evidence
### 5.1 Fresh topology check of the six main presets
For this page, the engine file was copied into an isolated temporary directory and executed using the project's existing Python environment. The original file's SHA-256 remained unchanged. No source code was modified and no training or dependency installation was required.

Each run used a $48\times48\times48$ grid, $2\times2\times2$ cells, a $20\times20\times20$ mm sampling domain, $C=0$, and field-band parameter $\tau=0.5$. All six runs returned successful meshes, reported watertight status, and independently had exactly two incident faces per unique edge.

| Preset | Triangles | Euler characteristic | Watertight |
| --- | ---: | ---: | --- |
| Gyroid | 91,884 | −102 | Yes |
| Primitive | 71,360 | −64 | Yes |
| Diamond | 113,068 | −230 | Yes |
| IWP | 91,496 | −196 | Yes |
| Neovius | 77,776 | −1,064 | Yes |
| BCC | 47,016 | −300 | Yes |

These are topology checks at one stated configuration, not mechanical, flow, or print benchmarks. The Gyroid's measured coordinate bounds were approximately $-0.0851$ to $20.0851$ mm on each axis, illustrating the small exterior extension introduced by interpolated padding caps.

## Discussion
The central engineering decision is to construct a finite solid before extracting its boundary. Periodic evaluation, field banding, negative padding, and explicit coordinate scaling make the path reproducible; post-extraction inspection exposes whether a particular result is closed.

Closure and geometric accuracy answer different questions. Resolution determines how well the grid captures narrow features and curvature. The field gradient influences local wall width. Padding affects final bounds. A watertight flag addresses connectivity, while printing also depends on dimensions, minimum feature size, orientation, support, and material. Self-intersection and minimum-wall checks would strengthen the export contract.

Custom expressions currently use a restricted evaluation namespace. A parser with an explicit operator/function allowlist would make the contract clearer. The procedural expression helper generates symbolic candidates; the model-loading hook is a stub in this source. This paper therefore attributes the geometry to equation evaluation and numerical meshing.

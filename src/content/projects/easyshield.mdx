## Abstract
EasyShield is a face presentation-attack detection pipeline developed as a liveness gate for identity recognition. Its contribution includes the data-production tools and inspection interfaces surrounding a YOLOv12-nano model: face extraction, augmentation, curation, detection-label generation, training, and live evaluation. The source implements two execution paths: continuous Windows inference and a five-frame Linux scan with confidence filtering and majority aggregation. This paper specifies the crop-to-decision contract, distinguishes offline and live face localization, and examines the class-mapping assumptions that connect training labels to deployment. The repository reports 92.30% accuracy on an 8,000-image comparison; these are published project results, rather than a new benchmark run for this page.

**Keywords:** presentation-attack detection; liveness; dataset curation; edge inference; decision thresholds; YOLO.

## System specification
### 2.1 Liveness before identity
A face detector locates a candidate region. The liveness model then evaluates evidence of a real face or a presentation attack in that region and its surrounding context. Identity recognition is a separate downstream responsibility in [NiotoShield](/projects/niotoshield). A liveness score alone does not establish a person's identity.

The implementation uses detection-style YOLO outputs: bounding-box classes and confidence values from `result.boxes`, rather than a classification-head probability vector. A cropped region is therefore converted into a binary liveness decision by interpreting the detector's returned class and score.

| Layer | Input | Responsibility |
| --- | --- | --- |
| Offline preparation | Images and videos | Extract and curate face-centered samples |
| Dataset packaging | Curated real / fake images | Generate normalized boxes and a train / validation / test split |
| Live localization | Camera frames | Locate faces with an OpenCV Haar cascade |
| Liveness model | Resized contextual crop | Return detection classes and confidence |
| Decision interface | Accepted predictions | Display real / attack evidence and scan aggregation |

### 2.2 Contextual cropping
The live model receives more than a tightly cut face. The code expands a detected face box by padding proportional to its width, clips the crop to the camera frame, and resizes it to $640\times640$. Context can retain useful evidence of a screen, printed sheet, or presentation boundary. The displayed rectangle uses a different, smaller padding; it should not be confused with the actual model input.

For face box $(x,y,w,h)$ in a frame of width $W$ and height $H$, the model crop is defined by

$$
\begin{aligned}
p&=\lfloor1.5w\rfloor,\\
x_1&=\max(0,x-p),\quad x_2=\min(W,x+w+p),\\
y_1&=\max(0,y-p),\quad y_2=\min(H,y+h+p).
\end{aligned}
\tag{1}
$$

Clipping handles faces near the frame edge. Resizing standardizes the tensor dimensions; it does not guarantee that each original crop has the same aspect ratio or amount of background.

## Method
### 3.1 Constructing a usable training set
The face-extraction tool uses MTCNN to obtain samples from photographs and video. Augmentation changes rotation, blur, brightness, contrast, and orientation. The filtering interface supports automatic face checks together with manual review, backup, and undo operations. These are separate stages: augmentation expands appearance variation, while curation determines whether a sample remains useful and correctly labeled.

The dataset preparation script uses an OpenCV DNN face detector to produce YOLO-format box labels. It shuffles the image collection and allocates 80% to training, 10% to validation, and 10% to testing. Each label contains a class and normalized box center, width, and height. This is an image-level split; evaluation of unseen identities, cameras, or recording sessions requires explicit grouping beyond the current random split.

### 3.2 Offline and live localization
MTCNN belongs to the extraction and filtering tools. The live Windows and Linux testers use a Haar cascade. The Windows path localizes faces at reduced frame resolution and maps coordinates back to the original frame. Face detections can be reused between localization steps, while the liveness model evaluates the contextual crops.

This separation keeps dataset production and interactive inference independently inspectable. It also creates a distribution boundary: the regions produced by offline tools and live localization may differ in framing, scale, and background. Crop consistency should therefore be evaluated alongside model accuracy.

### 3.3 Five-frame decision aggregation
The Linux tester collects up to five face crops, discards predictions below its selected confidence threshold, and counts the remaining real and fake outcomes. A scan reports real only when the real count strictly exceeds the fake count:

$$
\begin{aligned}
n_R&=\sum_{k\in\mathcal A}\mathbf{1}[\hat c_k=R],\\
n_F&=\sum_{k\in\mathcal A}\mathbf{1}[\hat c_k=F],\\
\hat d&=\begin{cases}R,&n_R>n_F,\\F,&n_R\le n_F.\end{cases}
\end{aligned}
\tag{2}
$$

Here $\mathcal A$ is the set of accepted crop predictions after confidence filtering. Ties and a scan with no accepted model outcomes follow the attack branch. A missing face or failed capture can also produce a separate interface error before aggregation. Average confidence is a displayed diagnostic, not a calibrated probability that authentication is safe.

## Implementation
### 4.1 Training and inspection tools
The trainer exposes epochs, batch size, optimizer, learning rate, worker count, caching, and device selection in a GUI. It invokes Ultralytics training and provides access to saved run artifacts. The surrounding tools make intermediate products visible: extracted faces, edited datasets, labels, training output, and live predictions can each be reviewed separately.

The Windows tester supports continuous camera/file evaluation with overlays. The Linux tester adds an explicit scan action and aggregation result, making the decision boundary visible to the operator rather than hiding it inside a frame loop.

### 4.2 The class-map contract
The inspected revision contains a material integration detail: dataset preparation and the benchmark use the ordering `0 = fake, 1 = real`, while the live testers interpret `0 = real, 1 = fake`. A deployed checkpoint must be paired with its actual saved class metadata. Numeric IDs cannot be treated as universal semantics across these scripts.

This paper and its diagrams use semantic labels **real** and **fake**. Verifying the checkpoint's class mapping is necessary before connecting liveness output to an identity gate. The original repository has been inspected without changing its training or inference code.

## Evidence
### 5.1 Repository-reported evaluation
The README reports the following results for its 8,000-image comparison. The table preserves that provenance; it does not imply an independently repeated experiment or a verified edge-device latency measurement.

| Metric | Repository-reported value |
| --- | --- |
| Accuracy | 92.30% |
| F1 | 92.68% |
| Attack presentation classification error | 6.25% |
| Bona fide presentation classification error | 2.50% |
| Average classification error | 4.38% |

The error-rate relationship is

$$
\mathrm{ACER}=\frac{\mathrm{APCER}+\mathrm{BPCER}}{2}.
\tag{3}
$$

These quantities distinguish attacks accepted as bona fide from bona fide presentations rejected as attacks. Their interpretation depends on the positive-class convention, threshold, and evaluation protocol. The benchmark script computes several metrics, but its score construction and class mapping require review before treating ROC/AUC outputs as fully validated.

## Discussion
The engineering strength is the complete route from raw footage to an inspectable liveness decision. Dataset tools expose quality issues early, contextual crops retain presentation evidence, and scan aggregation makes repeated observations explicit. The highest-value evaluation extensions are identity/session-disjoint splits, threshold sweeps with consistent class semantics, and device-specific latency measured across capture, localization, preprocessing, and inference.

A strong comparison also needs attack coverage beyond the training collection, including previously unseen presentation media and camera conditions. The reported result establishes a project evaluation record; it does not establish universal attack resistance or state-of-the-art status across protocols.

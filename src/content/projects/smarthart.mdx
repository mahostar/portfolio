## Abstract
SmartHart implements an end-to-end experimental pipeline for simulated multivariate vital signs: labeled data generation, seven-feature sequence construction, bidirectional recurrent classification, and online visualization. A ten-observation window is classified using the state attached to its final observation. The runtime reuses the training scaler and label map, maintains a sliding buffer, and displays predictions alongside the simulator's known labels. This paper describes the tensor contract, model architecture, training/runtime window differences, and a preprocessing-order issue relevant to evaluation. The system is a simulation-based academic prototype; the repository's reported accuracy describes synthetic scenarios rather than clinical performance.

**Keywords:** synthetic time series; sequence classification; bidirectional LSTM; feature consistency; online inference; monitoring interface.

## System specification
### 2.1 Data generation and labels
The simulator emits systolic and diastolic blood pressure, heart rate, oxygen saturation, respiratory rate, a timestamp, and a scenario label. The default generation interval is 0.5 seconds. Scenario dynamics couple changes across signals over time; labels include normal, cardiac-arrest, hypertensive-crisis, and septic-shock simulations.

These names identify synthetic generator scenarios. They do not constitute diagnoses produced or validated on patient recordings. The dashboard's controls adjust generation interval, plot history, and anomaly probability, allowing the same inference path to be exercised under different simulated transition rates.

### 2.2 Seven-feature tensor contract
Five generated measurements are supplemented with two derived features: pulse pressure $P_P$ and a guarded heart-rate-to-systolic-pressure ratio $S_I$:

$$
\begin{aligned}
P_P&=P_{\mathrm{sys}}-P_{\mathrm{dia}},\\
S_I&=\frac{H_R}{P_{\mathrm{sys}}+10^{-6}}.
\end{aligned}
\tag{1}
$$

The feature order is fixed: systolic pressure, diastolic pressure, heart rate, oxygen saturation, respiratory rate, pulse pressure, and the ratio above. Training and runtime must use the same order and persisted scaler. Each completed model input has shape $X\in\mathbb R^{B\times10\times7}$, with batch size $B=1$ for an online prediction.

## Method
### 3.1 Chronology, scaling, and window labels
Training validates required columns, parses timestamps, removes invalid rows, sorts observations chronologically, and derives the two additional features. `StandardScaler` transforms each feature using a saved mean and scale:

$$
\widetilde{x}_{t,j}=\frac{x_{t,j}-\mu_j}{\sigma_j}.
\tag{2}
$$

The default sequence length is ten and the training overlap parameter is zero, yielding stride ten. A sequence receives the label from its final row. An 80/20 chronological training/test split is made without shuffling. Keras reserves 20% of the training portion for validation.

The inspected preprocessing fits the scaler before splitting the sequences. Test-period feature distributions therefore influence the scaling parameters. A strict held-out evaluation should fit preprocessing only on training observations and apply those parameters to later periods. This is an evaluation boundary in the original implementation, which remains unchanged.

### 3.2 Bidirectional recurrent classifier
The first bidirectional LSTM has 128 units per direction and returns the full sequence, giving a $10\times256$ representation per sample. A second bidirectional LSTM has 64 units per direction and returns a 128-element vector. A 64-unit ReLU dense layer precedes the class softmax; dropout of 0.2 follows each recurrent stage and the intermediate dense layer.

For logits $z_c$ and final-row class $y$, the classifier uses

$$
\begin{aligned}
p_c&=\frac{e^{z_c}}{\sum_{k=1}^{C}e^{z_k}},\\
\mathcal L&=-\log p_y.
\end{aligned}
\tag{3}
$$

The inspected training configuration uses Adam with learning rate $10^{-3}$, batch size 32, and a maximum of 30 epochs. Early stopping monitors validation loss with patience five and restores weights from the minimum validation loss. $C$ is determined by the encoded labels; the supplied generator defines four scenario classes.

Bidirectional processing operates inside the already observed ten-row window. It does not require observations beyond that completed window at online inference time.

## Implementation
### 4.1 A three-artifact inference contract
Training saves the Keras model, fitted scaler, and class-label array. Runtime loads all three: the model alone is insufficient because its inputs depend on feature scaling and its numeric outputs depend on the persisted class order.

The online process computes the same seven features, transforms them with the saved scaler, reshapes the buffer to $(1,10,7)$, and maps the softmax argmax through the saved labels. It waits for ten observations before predicting.

### 4.2 Sliding online inference and UI scheduling
Training uses non-overlapping windows by default. Runtime advances the ten-row buffer by one observation, so neighboring predictions share nine rows. This provides frequent interface updates while introducing strong temporal dependence between adjacent decisions.

A background data loop generates observations and invokes the Tkinter scheduler for interface updates. The dashboard redraws live signal charts and prediction state through the UI event loop. Adjustable history length affects the displayed trace; the classifier's input length remains ten.

The runtime compares each prediction with the simulator's current known label. Its displayed moving accuracy uses the most recent 100 prediction outcomes:

$$
\begin{aligned}
A_t&=\frac{1}{m}\sum_{k=t-m+1}^{t}\mathbf{1}[\hat y_k=y_k],\\
m&=\min(100,n).
\end{aligned}
\tag{4}
$$

Here $n$ is the number of available prediction outcomes. This is an online diagnostic on overlapping synthetic windows, rather than an independent test-set estimate.

## Evidence
The repository README reports overall accuracy above 98% and approximately 93% for online operation. Those values are source-reported simulation results; no training or patient-data evaluation was rerun for this page. The training script provides confusion-matrix, classification-report, and ROC analysis code, while the live interface exposes scenario labels, predictions, and recent correctness.

The existing application and project media remain available in the gallery. New source-derived figures explain the feature/model contract and online state transition without inventing signal recordings, accuracy curves, or patient measurements.

## Discussion
The project demonstrates consistency across data generation, feature engineering, artifact persistence, inference, and visualization. Its most useful implementation distinctions are final-row sequence labels, training stride ten versus runtime stride one, and the dependence of every inference on a matched scaler and label map.

Further evaluation should isolate preprocessing to the training period, separate complete simulated episodes across splits, and report transition-level errors in addition to aggregate accuracy. Class imbalance and long normal intervals can hide missed scenario transitions. Results on this generator establish behavior within its synthetic assumptions; real sensor variability, missingness, and clinical generalization remain outside the demonstrated evaluation.
